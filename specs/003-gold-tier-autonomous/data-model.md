## Entity: Odoo Invoice

Represents a customer invoice created or read from the Odoo Community accounting system via JSON-RPC.

**Odoo Model**: `account.move` (with `move_type='out_invoice'`)
**Managed by**: `src/mcp/tools/odoo_invoice.py`

### Fields (JSON-RPC mapping)

| Field | Odoo Field | Type | Required | Description |
|-------|-----------|------|----------|-------------|
| `id` | `id` | integer | Yes (read) | Odoo record ID (auto-assigned) |
| `name` | `name` | string | No (auto) | Invoice reference number (e.g., "INV/2026/0001") |
| `partner_id` | `partner_id` | integer | Yes | Customer ID (from `res.partner`) |
| `partner_name` | `partner_id.name` | string | Yes (read) | Customer display name |
| `move_type` | `move_type` | string | Yes | Always `out_invoice` for customer invoices |
| `invoice_date` | `invoice_date` | string (YYYY-MM-DD) | Yes | Invoice date |
| `invoice_date_due` | `invoice_date_due` | string (YYYY-MM-DD) | Yes | Payment due date |
| `state` | `state` | string | Yes (read) | `draft`, `posted`, `cancel` |
| `payment_state` | `payment_state` | string | Yes (read) | `not_paid`, `in_payment`, `paid`, `partial`, `reversed` |
| `amount_total` | `amount_total` | float | Yes (read) | Total amount including tax |
| `amount_residual` | `amount_residual` | float | Yes (read) | Amount still owed |
| `currency_id` | `currency_id` | integer | No | Currency (defaults to company currency) |
| `invoice_line_ids` | `invoice_line_ids` | list | Yes | Line items (see below) |

### Invoice Line Item Fields

| Field | Odoo Field | Type | Required | Description |
|-------|-----------|------|----------|-------------|
| `name` | `name` | string | Yes | Line description |
| `quantity` | `quantity` | float | Yes | Quantity |
| `price_unit` | `price_unit` | float | Yes | Unit price |
| `tax_ids` | `tax_ids` | list[int] | No | Tax record IDs |

### State Transitions

```text
[Created via JSON-RPC] → state: draft
     │
     ▼
[action_post()] → state: posted (payment_state: not_paid)
     │
     ▼
[Payment recorded] → payment_state: paid (or partial)
```

**Odoo Model**: `account.payment`

## Entity: Financial Summary

Aggregated financial data for a date range, generated by querying Odoo. Not stored in Odoo — computed on demand.

**Managed by**: `src/mcp/tools/odoo_reports.py`
**Used by**: `src/briefing/briefing_generator.py`

### Fields

| Field | Type | Description |
|-------|------|-------------|
| `start_date` | string (YYYY-MM-DD) | Start of reporting period |
| `end_date` | string (YYYY-MM-DD) | End of reporting period |
| `total_revenue` | float | Sum of posted customer invoices in period |
| `total_expenses` | float | Sum of posted vendor bills in period |
| `outstanding_receivables` | float | Total unpaid customer invoices |
| `overdue_count` | integer | Number of invoices past due date |
| `overdue_amount` | float | Total amount overdue |
| `payments_received` | float | Sum of customer payments in period |
| `net_cash_flow` | float | payments_received - total_expenses |
| `invoice_count` | integer | Number of invoices created in period |
| `payment_count` | integer | Number of payments recorded in period |

### Example (returned by `get_financial_summary` tool)

## Entity: CEO Briefing

Weekly summary document generated every Monday morning. Stored as a Markdown file in the vault root.

**Location**: `vault/Briefing.md` (current week, overwritten each Monday)
**Archive**: `vault/Done/briefing-<YYYY-MM-DD>.md` (previous weeks)
**Managed by**: `src/briefing/briefing_generator.py`

### Frontmatter Fields (YAML)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `type` | string | Yes | Always `ceo_briefing` |
| `generated_date` | string (ISO 8601) | Yes | When the briefing was generated |
| `period_start` | string (YYYY-MM-DD) | Yes | Monday of the reporting week |
| `period_end` | string (YYYY-MM-DD) | Yes | Sunday of the reporting week |
| `data_sources` | list[string] | Yes | Which sources were available: `odoo`, `vault_logs`, `social` |
| `unavailable_sources` | list[string] | No | Sources that failed during generation |

### Body Sections (mandatory per FR-004)

1. **Financial Summary**: Revenue, expenses, receivables, overdue, cash flow. Trend indicators (up/down/stable) vs. previous week.
2. **Operational Status**: Items processed, plans generated, approvals executed, errors logged. Trend indicators.
3. **Social Media Activity**: Posts published by platform, engagement metrics (if available). Trend indicators.
4. **Bottlenecks & Risks**: Overdue invoices > 7 days, error count > 10, pending approvals > 48 hours, service outages > 1 hour.
5. **Recommended Actions**: AI-generated action items based on identified bottlenecks.

### Example

```markdown
---
type: ceo_briefing
generated_date: 2026-02-12T07:00:00Z
period_start: 2026-02-03
period_end: 2026-02-09
data_sources: [odoo, vault_logs, social]
unavailable_sources: []
---

# CEO Briefing: Week of Feb 3-9, 2026

## Financial Summary

| Metric | This Week | Last Week | Trend |
|--------|-----------|-----------|-------|
| Revenue | $15,000 | $12,000 | up |
| Expenses | $8,500 | $9,200 | down |
| Outstanding Receivables | $4,200 | $3,800 | up |

## Operational Status

- Items processed: 45 (last week: 38, trend: up)
- Plans generated: 8 (last week: 5, trend: up)
- Approvals executed: 12 (last week: 10, trend: up)
- Errors logged: 3 (last week: 7, trend: down)

## Social Media Activity

| Platform | Posts | Reach | Trend |
|----------|-------|-------|-------|
| Mastodon | 5 | N/A | stable |
| Facebook | 3 | 1,200 | up |
| X | 4 | N/A (Free tier) | stable |

## Bottlenecks & Risks

- **ALERT**: 2 invoices overdue > 7 days (Test Corp: $1,200, Acme Inc: $600)
- Social engagement metrics unavailable for X (Free tier limitation)

## Recommended Actions

1. Follow up on overdue invoices for Test Corp and Acme Inc
2. Consider upgrading X API tier for engagement metrics
3. Review 3 error logs from this week for recurring patterns
```

## Entity: Social Post (Extended)

Extends Silver's Approval Draft to support multi-platform targeting with per-platform content adaptation.

**Location**: `vault/Pending_Approval/<platform>-post-<timestamp>-<slug>.md`
**Managed by**: `/generate-social-post` skill, `src/approval/checker.py`
**Extends**: Silver Approval Draft

### Additional Frontmatter Fields (beyond Silver)

| Field | Type | Required | Description | New in Gold |
|-------|------|----------|-------------|-------------|
| `type` | string | Yes | `linkedin-post`, `mastodon-post`, `facebook-post`, `instagram-post`, `x-post` | LI/FB/IG/X types added |
| `platform` | string | Yes | `linkedin`, `mastodon`, `facebook`, `instagram`, `x` | NEW |
| `char_limit` | integer | No | Platform character limit (280 for X, 500 for Mastodon) | NEW |
| `engagement_metrics` | object | No | Post-publish metrics (populated after posting) | NEW |

### Per-Platform Constraints

| Platform | Character Limit | Media Required | Notes |
|----------|----------------|----------------|-------|
| LinkedIn | 3,000 | No | Share API v2, OAuth 2.0 |
| Mastodon | 500 | No | Default instance limit |
| Facebook | 63,206 | No | Practical: no limit |
| Instagram | 2,200 (caption) | Image required for feed posts | Text-only via Stories only |
| X (Twitter) | 280 | No | Hard limit, enforced pre-post |

## Entity: Ralph Wiggum Session

Represents one autonomous loop execution over a Plan.md file. Tracked in Plan.md frontmatter and logged to `/Logs`.

**Managed by**: `src/reasoning/ralph_wiggum.py`

### Frontmatter Fields (added to Plan.md during loop)

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `loop_status` | string | Yes | `running`, `paused`, `complete`, `timeout` |
| `loop_iteration` | integer | Yes | Current iteration count (0-10) |
| `loop_started` | string (ISO 8601) | Yes | When the loop began |
| `loop_last_iteration` | string (ISO 8601) | Yes | When the last iteration ran |
| `loop_max_iterations` | integer | Yes | Always 10 (from spec) |
| `loop_max_minutes` | integer | Yes | Always 30 (from spec) |
| `steps_total` | integer | Yes | Total checkbox steps in plan |
| `steps_completed` | integer | Yes | Steps checked off |
| `steps_awaiting_approval` | integer | Yes | Steps blocked on approval |
| `steps_failed` | integer | Yes | Steps that encountered errors |
| `nesting_depth` | integer | Yes | Current sub-plan depth (0-2) |

### State Transitions

```text
[/ralph-wiggum invoked on Plan.md]
     │
     ▼
[loop_status: running, iteration: 1]
     │
     ├─ Simple steps → execute → check off
     ├─ Action steps → create approval draft → mark "awaiting"
     ├─ Failed steps → log error → mark "failed" → continue
     │
     ▼
[All possible steps processed]
     │
     ├─ All done → loop_status: complete → move to /Done
     ├─ Approvals pending → loop_status: paused → wait for next iteration
     ├─ Iterations exhausted (10) → loop_status: timeout → log warning
     └─ Time exhausted (30 min) → loop_status: timeout → log warning
```

## Entity: Audit Log Entry

Structured log record appended to daily category log files.

**Location**: `vault/Logs/<category>-<YYYY-MM-DD>.md`
**Categories**: `mcp`, `classification`, `approval`, `loop`, `scheduler`
**Managed by**: `src/logging/audit_logger.py`

### Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `timestamp` | string (ISO 8601) | Yes | When the event occurred |
| `category` | string | Yes | Log category (determines file) |
| `action` | string | Yes | Action performed (e.g., `create_invoice`, `classify_item`) |
| `server` | string | No | MCP server name (for `mcp` category) |
| `tool` | string | No | MCP tool name (for `mcp` category) |
| `parameters` | object | No | Sanitized parameters (secrets redacted) |
| `result` | string | Yes | `success`, `failure`, `retry`, `skipped` |
| `duration_seconds` | float | No | Execution time |
| `error_message` | string | No | Error details (if result=failure) |
| `linked_artifact` | string | No | Related vault file (e.g., approval draft, plan) |
| `context` | string | No | Additional context (e.g., loop iteration number) |

## Entity: Service Health Status

Per-service operational state maintained in a JSON file, read by Dashboard and Briefing.

**Location**: `vault/.service_health.json`
**Managed by**: `src/health/service_health.py`
**Read by**: Dashboard.md update, briefing_generator.py

### Fields (per service)

| Field | Type | Description |
|-------|------|-------------|
| `service` | string | Service identifier: `odoo`, `linkedin`, `mastodon`, `facebook`, `instagram`, `x`, `gmail_smtp` |
| `status` | string | `operational`, `degraded`, `unavailable` |
| `last_ok` | string (ISO 8601) or null | Timestamp of last successful call |
| `last_error` | string (ISO 8601) or null | Timestamp of last failed call |
| `error_count` | integer | Consecutive failure count (resets on success) |
| `last_error_message` | string or null | Most recent error message (sanitized) |

### Status Transitions

```text
operational ──(3 consecutive failures)──> degraded
degraded ──(3 more failures)──> unavailable
unavailable ──(1 success)──> operational
degraded ──(1 success)──> operational
```

### Example

```json
{
  "odoo": {
    "status": "operational",
    "last_ok": "2026-02-12T10:05:23Z",
    "last_error": null,
    "error_count": 0,
    "last_error_message": null
  },
  "facebook": {
    "status": "unavailable",
    "last_ok": "2026-02-11T15:00:00Z",
    "last_error": "2026-02-12T10:15:02Z",
    "error_count": 6,
    "last_error_message": "Invalid access token"
  }
}
```
